架构分为 Qt 桌面、独立后端和共同使用的服务与存储层。收纳事务和重启恢复归 `IngestService`，目录查询归 `BundleService`，备份通过暂存和重建索引切换素材库。HTTP 和 MCP 通过现有接口交付。扫描 `app/` 及三个入口的 58 个 Python 模块、149 条静态本地导入边，未发现循环或服务层导入桌面层。耦合主要留在 `app_gui.py` 的窗口协调，以及管理页、最近卡片和详情都依赖全库查询。

### 本轮踩坑与修复

- 从源码运行时，Git 附带的空 `.gitkeep` 曾被算作素材。备份和空库判断现识别两个目录根部的空占位文件，恢复后保留目标占位文件；含用户内容的同名文件仍受保护。
- 主题目录中的普通附件过去能写入备份，恢复却将其当作 JSON。现在按原字节恢复，继续校验摘要和大小。组合含失效引用、归档大小超过恢复限额时，备份创建会在替换旧备份前失败。
- 原件及文件链接缺失时，库内仍可能有已提交或待恢复的入库记录。空库检查现查看入库记录，并保护只设置了自定义显示名的主题。回归覆盖恢复被拒绝后旧记录仍在。
- 字体链接和外部样式表现在依据页面最终生效的首个基础网址解析。音频用途搜索同时匹配存储值和界面文案，包括“音效”和“SFX”。
- 依赖告警要对照锁定版本，并按公告编号去重。默认分支报告的 56 条记录对应 28 个 Pillow 公告，12.3.0 落入这些公告的影响范围。开发分支的安装声明和发行约束已统一更新到修复版本 13。Linux 测试固定 Ubuntu 24.04，以便安装发行流程所需的 Python 3.12.10。[Pillow 13.0.0](https://pypi.org/project/pillow/13.0.0/)

### 后续优化顺序与验收方式

本轮验收源码为 `1fe9802`，使用 Pillow 13.0.0。三个平台各执行 613 项全量测试，macOS 和 Linux 各跳过 1 项平台专用检查，Windows 跳过 5 项，其余通过。另有 6 项 macOS Cocoa 和 10 项 Windows 原生窗口检查通过。真实素材库写入保护零触发。详细日志及性能脚本留存在本机 `build/architecture-review-20261118/`。[跨平台 CI](https://github.com/chenjinnan82-stack/Haypile-lite/actions/runs/44214112751)

1. **发布前验证真实操作。** 在 macOS 和 Windows 的浏览器旁用鼠标展开 C 环，一次点击环内空白处、环旁和卡片外的网页按钮，核对网页计数只增一次且浮层收起。再从地址栏拖网址，观察首次悬停及离开重入时是否闪烁或位移。把操作系统、显示缩放和结果写入[桌面验收记录](DESKTOP_ACCEPTANCE.md)。
2. **优先缩短“找回来”的等待。** 本机 Apple Silicon 上用 100 和 500 张不同的 24×24 PNG 建立隔离库，各预热一次、计时五次取中位数。查询最近 3 项从 33 ms 增至 169 ms，读取目录并生成管理页列表数据从 42 ms 增至 212 ms。该计时只含服务和列表数据构造。先让最近查询只校验要显示的条目，再让修改搜索词复用已读目录；新入库、人工修改、恢复和文件失效须刷新结果。建议用 1,000 项重复测量，目标为热态最近查询 P95 小于 100 ms，同时保留重复收纳排序、旧库回退与原件完整性检查。
3. **按用户任务验收发行候选。** 复走一次“收进来、重开找回来、交给别的应用”，记录卡住或需要提示的位置。上述检查通过后，从选定的干净提交一次性构建两个平台的包，验收启动、字体预览、备份恢复与 Agent 原件取用，再更新下载入口。若后续测量仍指向桌面协调瓶颈，优先拆出查询与列表更新，沿用现有窗口。

## 依赖方向

- 备份服务可以复用入库服务重建暂存索引；入库启动只调用独立的存储事务恢复，不加载备份服务。
- `storage_transactions.py` 管理快照锁、恢复记录、回退和持久化重命名，只依赖底层文件锁。
- `StorageRuntimeDB` 管理 SQL、恢复后的路径/最近顺序和 WAL 刷盘。备份模块不直接执行 SQL。
- GUI 调用服务层；服务层不导入 GUI 或 Qt。后端目录创建在应用生命周期启动阶段执行，导入后端模块本身不创建素材库。

## 查询与修改

- 素材查询通过 `ThemeRegistry.read_theme_contract` 在内存中兼容旧主题，不写回、不隔离文件；读取失败通过 `theme_read_errors` 报告。
- `ensure_theme_contract` 和 `upsert_image_asset` 是明确的创建、修复或修改入口。损坏主题保留在原处，用户重新确认用途时才隔离损坏记录并写入新内容；不会因为打开素材列表就发生修复。
- 最新批次、具体批次及最近素材读取不会调用数据库初始化/迁移；批次查询使用只读连接，未建立数据库时返回空结果。初始化和迁移仍由入库/启动流程负责。SQLite 自身可能使用 WAL/SHM 协调文件，这不等于执行业务写入。
- 音频用途更新与字体更新一样使用入库锁，防止备份取得主题与来源记录不一致的快照。
- GUI 通过公开的 `asset_path` 解析素材路径；路径边界和符号链接检查保留在服务内。

## 桌面协调

- C 环通过几何回调定位，通过 Qt 信号请求动作；原生输入读取在 `desktop_input.py`，无需素材卡片或草堆业务对象。
- 素材卡片通过信号请求收纳、取消、重试、清理候选和刷新提示，通过服务工厂读取素材。它仍读取草堆公开的操作状态和配置，这是应用协调依赖。
- 素材面板和卡片各自管理预览任务与退出状态。草堆只等待公开的 `shutdown_pending`，不逐个清理其他窗口的线程。
- 单项和批量 AI 整理结果先暂存，收到 QThread 的 `finished` 后才释放线程和更新界面；完成通知尚未处理时仍禁止重试，退出时禁止启动新任务。只接受当前任务的信号，旧任务延迟通知不会清理新任务。
- 进度显示、注意提示和卡片消息通过窗口方法更新；共享字体标签不再借用其他窗口的私有方法。
- Agent 配方与素材 handoff 构造归入已有 `handoff.py`，草堆无需调用素材面板生成数据。

保留 Qt 父子生命周期、应用入口对窗口与服务的组装，以及服务对配置/存储的调用。`app_gui.py` 仍较大；仅把代码移到更多文件不会进一步改变这些边界，因此没有新增通用控制器框架、接口层或依赖注入容器。
